# Manual Review Remediation Plan

هذا الملف يحول ملاحظات `manual review.pdf` إلى خطة تنفيذ عملية لتحسين واجهات النظام، تجربة الاستخدام، وتكامل الفرونت مع الباك.

## الهدف

- إصلاح الأخطاء الوظيفية والمرئية المذكورة في ملف المراجعة.
- توحيد سلوك الواجهات بين الصفحات المتشابهة.
- منع إظهار Actions أو صلاحيات غير مدعومة فعليًا من الباك.
- تحسين وضوح الـ UI/UX في صفحات الإدارة والسكرتارية والبيانات.

## مخرجات التنفيذ المتوقعة

- تنقل أوضح بين القوائم، القوائم الفرعية، وصفحات التفاصيل.
- جداول موحدة في الـ actions والحالات والنتائج الفارغة.
- رسائل نجاح وخطأ أوضح ومترجمة بشكل متسق.
- عرض بيانات مفهوم للمستخدم بدل القيم التقنية أو الـ keys الخام.
- مواءمة الواجهة مع صلاحيات الباك الحقيقية.
- إزالة أي تضليل بصري يوحي بإمكانية تنفيذ عملية غير مدعومة.

## أولويات التنفيذ

### P0 - أخطاء تؤثر على الاستخدام أو تعرض صلاحيات خاطئة

1. غياب مسارات الرجوع الصحيحة في أغلب الصفحات.
2. غموض أو غياب `actions` في الجداول.
3. عرض الحالة بدون طريقة واضحة لتغييرها أو قبول/رفض الطلب.
4. إظهار صلاحيات أو أزرار تعديل للـ admin بينما الباك يرفض العملية.
5. عرض بيانات خام أو خاطئة مثل `patientId` بدل اسم المريض.
6. مشاكل تكامل تجعل البيانات لا تظهر بسبب أسماء حقول أو قيم enum غير مطابقة.
7. عرض `object Object` أو قوالب رندر معطوبة.

### P1 - مشاكل UX واتساق بصري

1. أماكن النتائج الفارغة أو الرسائل غير واضحة.
2. اختلاف أحجام الخطوط بين بعض الصفحات.
3. حقول أو صناديق إدخال صغيرة أو غير مقروءة.
4. رسائل الويب أضعف من المطلوب في حالات النجاح أو الرفض أو القبول.
5. خلط لغوي عربي/إنجليزي في بعض التسميات مثل `data entry`.

### P2 - تحسينات تنظيمية وهيكلية

1. فصل أنواع الطلبات المتشابهة داخل واجهات التحقق.
2. توضيح دورة الحياة والحالات الخاصة بالمحتوى الطبي.
3. جعل بعض الشاشات أكثر مرونة بدل الاعتماد على تدفقات ثابتة `fixed`.
4. توثيق القيود التي يجب ألا يتحكم بها الـ admin من الواجهة.

## قائمة المشاكل والحلول المقترحة

### 1. التنقل والرجوع بين الصفحات

**المشكلة**

- يوجد نقص في `routes` أو مسارات العودة للصفحة السابقة أو الصحيحة في عدة صفحات.

**الأثر**

- المستخدم يضيع داخل صفحات التفاصيل.
- الرجوع يعتمد على المتصفح بدل مسار واضح داخل النظام.

**المطلوب**

- إضافة زر رجوع ثابت في جميع صفحات التفاصيل.
- اعتماد breadcrumb أو عنوان سياقي يوضح: القائمة > الصفحة > التفاصيل.
- عند الدخول من جدول إلى صفحة تفاصيل، يجب حفظ مسار الرجوع المنطقي وليس فقط `history.back()`.

**أماكن متوقعة للمراجعة**

- `frontend/src/constant/adminPageMeta.ts`
- `frontend/src/layouts/*`
- صفحات التفاصيل تحت:
  - `frontend/src/pages/admin/*`
  - `frontend/src/pages/doctor/*`
  - `frontend/src/pages/secretary/*`

### 2. عدم وضوح أو غياب الـ actions داخل الجداول

**المشكلة**

- في أغلب الجداول، أزرار الإجراء غير واضحة أو غير موجودة أو موزعة بشكل غير موحد.

**الأثر**

- المستخدم لا يعرف أين ينفذ القبول أو الرفض أو التفعيل أو التعطيل.
- نفس الإجراء يظهر مرة مباشرة داخل الجدول ومرة داخل صفحة التفاصيل ومرة غير موجود.

**المطلوب**

- إنشاء معيار موحد لكل جدول:
  - عمود حالة.
  - عمود إجراءات واضح.
  - قائمة إجراءات موحدة أو أزرار أساسية حسب نوع الكيان.
- استخدام نفس نمط الأزرار في جميع الجداول الإدارية.
- منع إظهار أي Action إذا لم يكن مدعومًا من الباك أو الصلاحية.

**أماكن متوقعة للمراجعة**

- `frontend/src/components/admin/*`
- `frontend/src/pages/admin/*`
- `frontend/src/components/ui/*`

### 3. صفحة الأطباء وطلبات التحقق غير واضحة

**المشكلة**

- حالة الطبيب معروضة، لكن آلية القبول أو الرفض غير واضحة.
- هناك تداخل بين طلبات التحقق وطلبات تغيير البروفايل.

**الأثر**

- صعوبة على الإدارة في معرفة هل الصفحة مخصصة لقبول حسابات الأطباء أم لتغيير بياناتهم.
- خلط بين نوعين مختلفين من workflows.

**المطلوب**

- فصل واضح بين:
  - `verification requests`
  - `doctor profile change requests`
- إضافة badge أو label يحدد نوع الطلب بوضوح.
- في صفحة التفاصيل يجب عرض:
  - نوع الطلب
  - الحالة الحالية
  - الإجراء المتاح
  - سبب الرفض إن وجد
  - من أنشأ الطلب ومتى

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/verification-requests/*`
- `frontend/src/pages/admin/doctor-profile-change-requests/*`
- `frontend/src/components/admin/verification-requests/*`
- `frontend/src/components/admin/doctor-profile-change-requests/*`

### 4. نتائج السجلات والرسائل الفارغة

**المشكلة**

- مكان النتيجة في صفحة السجلات غير واضح من ناحية UX.

**الأثر**

- صعوبة فهم ما إذا كان التحميل انتهى أو لا توجد نتائج أو يوجد خطأ.

**المطلوب**

- توحيد حالات الجدول:
  - loading
  - empty
  - error
  - loaded
- وضع الرسالة أو النتيجة في مركز بصري واضح.
- إضافة CTA مناسب عند الفراغ مثل إعادة التصفية أو مسح الفلاتر.

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/system-logs/*`
- `frontend/src/components/common/empty-state.tsx`
- `frontend/src/components/admin/skeletons/*`

### 5. عرض قيم تقنية بدل نصوص مفهومة

**المشكلة**

- يتم عرض `key` أو قيم enum خام بدل نص مفهوم للمستخدم مثل `cardiology`.
- الفرونت يقبل `SPECIALIZATION` قديمًا بينما الباك يقبل فقط `DOCTOR_SPECIALIZATION`.

**الأثر**

- تجربة استخدام ضعيفة.
- أخطاء تكامل عند الحفظ أو الفلترة أو الإنشاء.

**المطلوب**

- فصل قيمة التخزين عن قيمة العرض.
- إنشاء mapper موحد للـ enums والـ labels.
- إزالة دعم القيم legacy من النماذج إذا لم تكن مدعومة من الباك.
- مراجعة جميع نماذج التخصصات للتأكد من إرسال القيمة الصحيحة فقط.

**أماكن متوقعة للمراجعة**

- `frontend/src/hooks/shared/useDoctorSignupSpecialties.ts`
- `frontend/src/lib/auth/doctorSpecialties.ts`
- `frontend/src/pages/admin/doctor-specializations/*`
- `frontend/src/lib/admin/types.ts`

### 6. جودة الرسائل والتنبيهات

**المشكلة**

- بعض الرسائل الحالية أضعف من المطلوب أو غير واضحة.

**الأثر**

- المستخدم لا يفهم هل العملية نجحت أم فشلت أو ماذا يفعل بعد ذلك.

**المطلوب**

- تحسين رسائل:
  - قبول طلب التحقق
  - رفض الطلب
  - الأخطاء الناتجة عن التكامل
  - نجاح الحفظ أو التحديث
- توحيد tone الرسائل: قصيرة، واضحة، عملية.
- ربط الرسائل بحالة العملية الفعلية وليس بتوقعات الواجهة.

**أماكن متوقعة للمراجعة**

- `frontend/src/lib/admin/userFacingError.ts`
- `frontend/src/lib/queryErrorHandling.ts`
- `frontend/src/i18n/apiMessageKeys.ts`
- `frontend/src/ui/ToastProvider.tsx`

### 7. ربط أفضل بين الواجهات وصفحات التفاصيل

**المشكلة**

- بعض العناصر كان الأفضل أن تنقل لصفحة الطبيب أو التفاصيل مباشرة.

**الأثر**

- رحلة استخدام مقطعة وغير مباشرة.

**المطلوب**

- كل صف قابل للإدارة يجب أن يدعم:
  - فتح التفاصيل
  - تنفيذ الإجراء الأساسي
  - الوصول السريع للكيان المرتبط
- مثال: إذا كانت المعلومة تخص طبيبًا، يجب أن يكون الوصول إلى ملف الطبيب مباشرًا وواضحًا.

### 8. مشكلة الـ slug بالعربية

**المشكلة**

- يوجد `slug` باللغة العربية.

**الأثر**

- احتمال مشاكل في الروابط، التوافق، الفهرسة، والاعتماد على قيم غير مستقرة.

**المطلوب**

- اعتماد `slug` إنجليزي أو لاتيني موحد.
- إبقاء العربية للعرض فقط.
- إضافة validation يمنع إدخال slug غير مطابق للقاعدة.

### 9. المحتوى الطبي وهيكلته الحالية غير صحيحة

**المشكلة**

- نظام `medical content` أو المكتبة الطبية فيه مشاكل أساسية:
  - طلب مصدر خبر دون وجود مكان واضح له في الـ form
  - دورة حياة غير واضحة
  - غياب فصل بين ما أنشأه admin وما أنشأه data entry
  - حالات data entry غير واضحة
  - التدفق الحالي ثابت وغير dynamic

**الأثر**

- صعوبة إدارة المحتوى.
- أخطاء عملية في الإنشاء والمراجعة والنشر.

**المطلوب**

- إعادة تعريف workflow المحتوى الطبي:
  - draft
  - in review
  - approved
  - rejected
  - published
  - archived
- إضافة حقول واضحة للمصدر إذا كان مطلوبًا.
- إظهار منشئ العنصر ودوره.
- فصل الواجهات أو الفلاتر حسب نوع المحتوى وحالته ومنشئه.
- إعادة تصميم النماذج لتدعم dynamic fields عند الحاجة.

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/medical-content/*`
- `frontend/src/pages/data-entry/medical-content/*`
- `frontend/src/components/admin/medical-content/*`
- `frontend/src/lib/admin/content/*`

### 10. أخطاء رندر من نوع `object Object`

**المشكلة**

- توجد حالات رندر خاطئة تعرض `object Object`.

**الأثر**

- كسر بصري مباشر وفقدان المعنى.

**المطلوب**

- مراجعة جميع أعمدة الجداول وبطاقات التفاصيل التي تعرض كائنات مركبة.
- إضافة formatters واضحة للأنواع:
  - arrays
  - objects
  - nullable values
- عدم تمرير object مباشرة داخل JSX.

### 11. قيود يجب ألا يتحكم بها الـ admin

**المشكلة**

- توجد ملاحظات على عناصر مثل الزمرة أو غيرها لا يجب أن يعبث بها الـ admin.

**الأثر**

- الواجهة توحي بصلاحيات غير صحيحة.
- خطر تعديل بيانات حساسة أو مرجعية.

**المطلوب**

- إخفاء أزرار التعديل أو الحذف للعناصر المرجعية الحساسة.
- عرضها كبيانات للقراءة فقط إذا كان هذا هو السلوك الصحيح.
- توضيح السبب في النص المساعد عند الحاجة.

### 12. صناديق أو حقول غير واضحة بصريًا

**المشكلة**

- بعض الصناديق صغيرة أو النص داخلها غير واضح.

**الأثر**

- تعب بصري وصعوبة إدخال أو قراءة البيانات.

**المطلوب**

- توحيد ارتفاع الحقول.
- تحسين التباين والحواف والمسافات الداخلية.
- مراجعة الـ textarea والحقول متعددة القيم خصوصًا في صفحات الإدارة.

### 13. الأمان والجلسات

**المشكلة**

- لا يوجد تسجيل خروج من كل الأجهزة.

**الأثر**

- نقص واضح في إدارة الجلسات والأمان.

**المطلوب**

- إضافة خيار:
  - تسجيل الخروج من هذا الجهاز
  - تسجيل الخروج من كل الأجهزة
- إظهار تأكيد واضح قبل التنفيذ.

**أماكن متوقعة للمراجعة**

- `frontend/src/components/auth/logout-confirm-dialog.tsx`
- `frontend/src/lib/devices/*`
- `frontend/src/components/app/DeviceRegistrationBridge.tsx`

### 14. واجهات data entry فيها عناصر hardcoded أو غير مربوطة

**المشكلة**

- `إيقاف/تفعيل الحساب غير متاح حالياً hardcoded`
- الـ actions غير مربوطة أو غير واضحة.
- هناك خلط لغوي في تسمية `data entry`.

**الأثر**

- الواجهة تبدو منجزة بصريًا لكنها غير عاملة فعليًا.

**المطلوب**

- إزالة أي action شكلي غير حقيقي.
- إذا كانت العملية غير مدعومة: إخفاؤها بدل تعطيلها بصمت.
- توحيد التسمية عربيًا وإنجليزيًا في كل الصفحات والقوائم.

### 15. إدارة ملفات المريض من قبل admin بشكل واسع

**المشكلة**

- الأدمن يستطيع عرض وإدارة ملفات المريض بالكامل:
  - list
  - view metadata
  - download
  - upload
  - delete

**الأثر**

- هذا على الأغلب أوسع من المطلوب وظيفيًا أو أمنيًا.

**المطلوب**

- مراجعة ما الذي يجب أن يراه أو يفعله الـ admin فقط.
- حصر العمليات في الحد الأدنى اللازم.
- إذا كانت بعض العمليات ممنوعة وظيفيًا، يجب إزالتها من الواجهة.

### 16. عرض المواعيد باستخدام `patientId` فقط

**المشكلة**

- اسم المريض لا يظهر في عرض المواعيد، ويظهر فقط `patientId`.

**الأثر**

- صعوبة في القراءة السريعة والعمل اليومي.

**المطلوب**

- عرض:
  - اسم المريض أولًا
  - ثم الـ ID كمعلومة ثانوية
- إضافة fallback واضح إذا كان الاسم غير متوفر.

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/appointments/*`
- `frontend/src/pages/secretary/appointments/*`
- `frontend/src/hooks/admin/appointments/*`

### 17. صفحة السكرتيرة تعرض صلاحيات قابلة للتعديل بينما الباك يرفض

**المشكلة**

- الأدمن يرى واجهات تسمح بتعديل صلاحيات السكرتيرة أو ملفها، لكن الباك يرفض ذلك.

**الأثر**

- تضليل مباشر للمستخدم.
- فقدان الثقة في النظام.

**المطلوب**

- جعل شاشة صلاحيات السكرتيرة `read-only` إذا كانت الصلاحيات غير قابلة للتعديل.
- إظهار فقط ما يمكن فعله فعليًا مثل:
  - إيقاف الحساب
  - إعادة التفعيل
- إزالة أي زر إضافة أو تعديل لا يملك backend contract صالحًا.

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/secretaries/*`
- `frontend/src/hooks/secretary/useSecretaryPermissions.ts`
- `frontend/src/lib/secretary/permissions.ts`

### 18. الخدمات ومزودو الخدمة وأنواع الخدمات

**المشكلة**

- توجد مشاكل متعددة في الخدمات والمنشآت ومزودي الخدمة والديزاين.

**المطلوب**

- تخصيص ملف مراجعة منفصل تفصيلي لهذه المجموعة.
- لكن ضمن هذا الملف يجب اعتماد قواعد عامة:
  - توحيد الجداول
  - توحيد النماذج
  - توحيد الحالات
  - منع التضارب بين service type و provider و service

### 19. قبول طلب التحقق ورسالة النجاح

**المشكلة**

- رسالة قبول طلب التحقق تحتاج تحسين UX.

**المطلوب**

- رسالة نجاح تتضمن:
  - اسم الطبيب
  - نوع العملية
  - الحالة الجديدة
  - ماذا سيحدث لاحقًا إن وجد

### 20. المنشآت بعد الحذف

**المشكلة**

- بعد حذف المنشأة، يجب أن يبقى التعديل ممكنًا إذا كان المقصود إرجاعها `active`.

**الأثر**

- عدم القدرة على الاستعادة أو إعادة التفعيل من نفس السجل.

**المطلوب**

- اعتماد soft delete في الواجهة إذا كان الباك يدعم ذلك.
- إظهار حالة المنشأة بوضوح:
  - active
  - inactive
  - deleted
- السماح بإجراء الاستعادة إن كان مدعومًا.

### 21. طلبات الوصول لا تعرض البيانات بسبب mismatch

**المشكلة**

- بيانات مثل `name`, `email`, `phone` لا تظهر لأن الداتا المرجعة ناقصة أو مسماة بشكل مختلف عن المتوقع في الفرونت.

**الأثر**

- كسر مباشر في الصفحة وعدم ظهور معلومات الطلب.

**المطلوب**

- مراجعة mapper استجابة `access requests`.
- عدم افتراض أسماء حقول غير موثقة.
- إضافة fallback وعرض تحذير داخلي إذا كانت الحقول ناقصة.

**أماكن متوقعة للمراجعة**

- `frontend/src/pages/admin/access-requests/*`
- `frontend/src/hooks/admin/access-requests/*`
- `frontend/src/lib/admin/access-requests/*`
- `docs/openapi.json` عند بدء التنفيذ الفعلي

### 22. اختلافات الخطوط والأحجام

**المشكلة**

- توجد صفحات فيها اختلاف في حجم أو نوع الخط دون سبب واضح.

**الأثر**

- النظام يبدو غير متسق.

**المطلوب**

- مراجعة typography scale بالكامل.
- تثبيت أحجام موحدة للعناوين والنصوص ووصف البطاقات والجداول.
- مراجعة الصفحات التي تستخدم مكونات خاصة بدل النظام الموحد.

## تحسينات UI/UX عامة يجب تطبيقها أفقيًا

### الترويسات والهوية السياقية

- كل صفحة تحتاج:
  - عنوان واضح
  - وصف قصير
  - زر رجوع عند الحاجة
  - actions رئيسية في مكان ثابت

### الجداول

- توحيد الأعمدة الأساسية: الاسم، الحالة، آخر تحديث، الإجراءات.
- دعم empty state وloading state وerror state.
- جعل الصف قابلًا للنقر عند وجود صفحة تفاصيل.

### النماذج

- منع الحقول المطلوبة غير المرئية.
- إظهار validation inline.
- تعطيل زر الحفظ أثناء الإرسال.
- ترجمة جميع الـ labels والأخطاء بشكل موحد.

### الرسائل

- عدم عرض رسائل تقنية خام للمستخدم.
- استخدام رسائل موجهة للفعل:
  - تم الحفظ
  - تعذر الحفظ
  - تم قبول الطلب
  - تم رفض الطلب

### الصلاحيات

- الواجهة يجب أن تعكس ما تسمح به API فقط.
- أي صلاحية غير مدعومة يجب ألا تظهر كزر قابل للتنفيذ.

## ترتيب التنفيذ المقترح

### المرحلة 1

- إصلاح التنقل والرجوع.
- توحيد actions الجداول.
- إصلاح صفحات الأطباء وطلبات التحقق وتغيير البروفايل.
- منع إظهار الصلاحيات الوهمية للسكرتيرة وواجهات data entry.

### المرحلة 2

- إصلاح mappers العرض والقيم الخام والـ enums.
- تحسين الرسائل والتنبيهات.
- إصلاح access requests وappointments وpatient labels.
- إصلاح مشاكل `object Object`.

### المرحلة 3

- إعادة تنظيم medical content workflow.
- تحسين typography والاتساق البصري.
- مراجعة الملفات الحساسة وإدارة patient files والمنشآت.

## معايير القبول

- لا توجد صفحة تفاصيل بدون رجوع واضح.
- لا يوجد جدول بدون actions مفهومة أو بديل واضح.
- لا يظهر أي زر تعديل أو إضافة إذا كان الباك لا يدعمه.
- لا تظهر قيم تقنية خام للمستخدم النهائي.
- جميع الرسائل الأساسية مفهومة ومترجمة.
- جميع صفحات الطلبات تعرض نوع الطلب، حالته، والإجراء المتاح بوضوح.
- الصفحات المتأثرة تستخدم نفس منطق الحالات: loading / empty / error / success.

## ملاحظات تنفيذية

- أي إصلاح مرتبط بالـ backend contract يجب مراجعته من `docs/openapi.json` قبل التنفيذ.
- ملفات `services` و`providers` و`medical content` قد تحتاج ملفات مراجعة تفصيلية منفصلة بسبب كثرة الملاحظات.
- يفضل تنفيذ الإصلاحات على شكل دفعات صغيرة حسب المجال:
  - navigation
  - tables
  - verification flows
  - secretary permissions
  - access requests
  - medical content
